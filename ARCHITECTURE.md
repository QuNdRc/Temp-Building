# Архитектурная карта проекта

Это не приложение, а **арсенал заготовок** для строительного хакатона. Важно понимать,
что здесь два разных слоя: **переиспользуемые шаблоны** (универсальные) и
**решения тестовых кейсов** (кейс-специфичные, не универсальные — и это нормально).

```
Solution6/
├── run.py                      ← единая точка входа
├── ARCHITECTURE.md             ← этот файл
├── README.md                   ← быстрый старт
├── requirements.txt            ← Python-зависимости
│
├── 01_optimization_cpp/        ← ШАБЛОН: перебор вариантов (C++)
├── 02_cpm_monte_carlo/         ← ШАБЛОН: CPM + Монте-Карло (C++)
├── 03_data_pipeline_py/        ← ШАБЛОН: CSV/JSON → таблица → агрегаты
├── 04_llm_json_py/             ← ШАБЛОН: локальная LLM → JSON
├── 05_geometry_py/             ← ШАБЛОН: shapely-геометрия
├── 06_computer_vision_py/      ← ШАБЛОН: OpenCV по фото
├── 07_calcs_cpp/               ← ШАБЛОН: Wood-Armer + осадка (скелет)
├── 08_docs_rules_py/           ← ШАБЛОН: LLM-разбор + проверка правил
├── 09_assignment_cpp/          ← ШАБЛОН: венгерский алгоритм
├── 10_report_docx_py/          ← ШАБЛОН: генератор ПЗ в Word
│
└── tests/                      ← решения реальных кейсов (НЕ шаблоны)
    ├── case1/                  ← «Стройгенплан»: CV + оптимизация + CPM
    ├── case2/                  ← «Бытовой городок»: CV + расстановка + CPM
    └── case3/                  ← «Модель, смета, график»: IFC-парсинг
```

## Слой 1: шаблоны (`01_*` … `10_*`)

**Это то, что переиспользуется на любом кейсе.** Каждый шаблон автономен:
его можно скопировать в рабочую папку нового кейса и доработать.

| Шаблон | Ядро (что переиспользуешь) | Как адаптировать под задачу |
|---|---|---|
| [`01_optimization_cpp`](01_optimization_cpp) | `opt::anneal()`, `opt::hill_climb()`, `opt::random_search()` в `optimize.hpp` | пишешь свои `score()`, `mutate()`, `random()` |
| [`02_cpm_monte_carlo`](02_cpm_monte_carlo) | `cpm::solve()`, `cpm::monte_carlo()`, `cpm::p_finish()` | подаёшь свои рёбра графа |
| [`03_data_pipeline_py`](03_data_pipeline_py) | `read_table()`, `clean()`, `aggregate()`, `anomalies()`, `plot()` | подставляешь свой CSV/JSON |
| [`04_llm_json_py`](04_llm_json_py) | `llm_json()` + `extract_json()` | меняешь промпт под поля |
| [`05_geometry_py`](05_geometry_py) | `rect()`, `intersection_area()`, `coverage()`, `bin_pack()` | описываешь свои полигоны |
| [`06_computer_vision_py`](06_computer_vision_py) | `detect_defects()`, `annotate()` | подбираешь пороги под задачу |
| [`07_calcs_cpp`](07_calcs_cpp) | `wood_armer()`, `settlement()` | подставляешь свои коэффициенты СП |
| [`08_docs_rules_py`](08_docs_rules_py) | `check_rules()` + `report()` | меняешь правила под нормы |
| [`09_assignment_cpp`](09_assignment_cpp) | `assign::hungarian()` | подаёшь матрицу стоимости |
| [`10_report_docx_py`](10_report_docx_py) | `Report` (секции, таблицы, картинки) | наполняешь своими результатами |

**Принцип работы:** шаблоны дают 80% кода (движки, структуры, библиотечные обвязки).
Оставшиеся 20% — это твоя предметная логика: score-функция, формулы, правила, пороги.

## Слой 2: решения кейсов (`tests/case*`)

**Это НЕ шаблоны.** Это готовые решения конкретных задач, которые показывают,
как шаблоны собираются в цепочку. Они кейс-специфичны: координаты, формулы,
пороги заточены под конкретные входные файлы.

| Кейс | Что иллюстрирует | Какие шаблоны использует |
|---|---|---|
| [`case1`](tests/case1) | цепочка «CV → оптимизация → CPM» | 01, 02, 06 + точная геометрия |
| [`case2`](tests/case2) | полный цикл от плана до ПЗ | 06, 01, 10 |
| [`case3`](tests/case3) | IFC-парсинг + смета + график | 10 + ifcopenshell |

## Ключевые архитектурные уроки (выстраданы на кейсах)

1. **Проверку ограничений оптимизации НЕ завязывай на результат распознавания.**
   В case1 первоначальная цепочка «сетка → размещение» дала сбой: кран встал
   на неверно распознанное здание. Проверку надо вести по аналитическим
   прямоугольникам (`geom_case1.py`), а не по CV-сетке.

2. **CV-пороги по абсолютной яркости ломаются на засветке.**
   В case1 новые здания дали IoU 0.35 на фиксированных порогах. Лечится
   адаптивным порогом (CLAHE) или контурным детектом, а не подбором числа.

3. **Единицы в IFC читай из `IfcSIUnit`, а не угадывай.**
   В case3 всё в миллиметрах — забытый множитель 0.001 сломал этажность.

4. **Объём проёма — это пересечение AABB, а не полный объём.**
   В case3 простое `w·h·d` дало 31 ложное нарушение R2 вместо 3.

5. **Один скрипт = один кейс = один `results.json` + один `otchet.docx`.**
   Так результат сразу готов к защите и не требует ручной сборки.

## Как быстро начать новый кейс

```bash
python run.py new caseX
```

Создаст `tests/caseX/` с каркасом `solve.py` (пустой шаблон решения + импорт
`Report` из `10_report_docx_py`). Дальше:
1. кладёшь входные файлы в `tests/caseX/`;
2. правишь `solve.py` под задачу, переиспользуя нужные шаблоны;
3. `python run.py run caseX` — запуск и генерация отчёта.

## Слои ответственности

```
входные данные (CSV/JSON/PNG/JPG/IFC)
        │
        ▼
[шаблон] читает/парсит   ← универсальный код, не трогаешь
        │
        ▼
[твой код] предметная логика ← меняешь под задачу
        │
        ▼
[шаблон] выводит results.json + otchet.docx ← универсальный код, не трогаешь
```
